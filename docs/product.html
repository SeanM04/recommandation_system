Decomposition

One job, shown three offers at a time: put in front of each customer the offers they are most likely to take up, and get better with every response. Six capabilities deliver it.

Capabilities in detail

CapabilityFeaturesCodeRead more
1 · Recommend in real timeBuilds the context from the customer's profile (segment, device, contract, spend, province) and the moment (day, time of day, payday week, channel). Keeps only the offers the customer is eligible for. Ranks them with one of nine policies: the one in settings.yaml, or any other named in the request (?policy=). Answers with three offers.api/main.py (POST /invocations), api/services.py, domain.py, algorithms/API, Models
2 · Learn from every responseTurns each outcome into a reward (1 per take-up, or margin; a view 0; an ignored offer nothing). Records each outcome once (a repeat gets 409). Updates the serving policy's belief in one database transaction, forgetting a little first if the policy forgets. Updates to one segment queue on a lock of their own, so concurrent workers never deadlock.api/main.py (POST /response), algorithms/rewards.py, store/Policies, Architecture
3 · Record everythingThe event log keeps every app open with its full context, every offer shown with its position and score, and every response, so any model can be rebuilt from it. The options store holds what each policy believes. A nightly job rolls the log up into one row per day, policy, segment and offer.events/log.py, store/sql.py, events/daily.pyAPI: event log
4 · Prove it works5,000 simulated customers in five segments, with a hidden take-up probability for every customer, offer and moment, a response model (people read top-down) and a behaviour shift halfway through. All nine policies run on the identical app opens, 10 times, against an oracle that knows the truth.simulator/, evaluation/Simulated world, Results
5 · Show and explainA dashboard behind a sign-in: the live event log, three pages that tell the results as stories (which policy wins, how it explores, how it adapts), Try it, and user and key management. These docs, the README and the write-up.dashboard/, evaluation/story.py, exploration.py, adaptation.py, docs/Dashboard
6 · Run and securepython manage.py to migrate, create users and keys, and start everything. Accounts with roles, optional API keys. Docker Compose for the whole system. JSON logs, /health and /metrics. 200+ tests, linting, docs that fail the build when stale, and a hook that requires docstrings.cli.py, accounts.py, Dockerfile, docker-compose.yml, observability.py, tests/Workflows, Tools & quality

One app open, end to end

Capabilities 1, 2 and 3 meet in every app open. Steps 1–8 happen while the customer waits for their offers; steps 9–13 when they respond.

Built, and what production adds

Built

All six capabilities above, end to end, on a simulated world with a known answer: real-time ranking and learning, the event log, nine policies compared over 10 seeds, a signed-in dashboard that explains the results, and one-command runs with manage.py or Docker Compose.

Production adds

Learning off the request path (an event stream), customer features from a feature store, a permanent holdout and drift alerts, guardrails (fatigue caps, frequency limits, affordability checks for credit), single sign-on and a secrets manager, and a load test on Linux servers. The write-up explains each.

How it works

One loop, end to end

Every app open is ranked with what the previous responses taught. This page draws that loop once, from the customer's tap to the belief it changes, and then shows how the same loop is tested against a world whose answers are known.

The loop in one picture

Two API calls make up one turn of the loop. POST /invocations ranks offers when a customer opens the app; POST /response reports what the customer did with them. The database between them, Postgres (or SQLite when there is no .env), holds what has been learned, and every API worker shares it.

Step by step

The numbers match the diagram. The serving policy is thompson_segment_decay: Thompson sampling with one belief per customer segment and offer, and a little forgetting.

  1. Opens the app. The app sends POST /invocations with the customer id. It may also name a channel, ask for a different number of offers, or set the moment (a day, a time of day, payday week) for testing.
  2. Build the moment. The API looks the customer up in the customers table (segment, device, contract, spend, province) and adds the moment from the clock in Africa/Johannesburg: the day of the week, the time of day, and whether it is payday week for that segment. Salaried segments are paid on the 25th; pensioners in the first week, when SASSA grants are paid.
  3. Rank by drawing. The policy reads its belief about every offer this segment may be shown: one Beta(α, β) distribution per offer, kept in the options store. It draws one plausible take-up rate from each belief and shows the three highest draws. An offer it knows well draws close to its rate every time; one it knows little about draws widely and now and then wins a slot. That is all the exploration there is, with nothing to tune (how each policy ranks).
  4. Log, then reply. Before answering, the API writes the app open with its full context to invocations, and each offer shown, with its position and its draw, to impressions, in one transaction. The reply carries an invocation_id that the response will quote.
  5. Responds. The customer takes an offer up, looks at it and moves on, or never notices it. The app reports each outcome to POST /response.
  6. Score and log once. The API reads the invocation back from the event log: which policy served it, the context it was ranked in, and which offers were shown (an offer that wasn't shown gets 422). The outcome becomes a reward: 1 for a take-up, 0 for a view, and no update for an ignored offer, because an offer nobody noticed says nothing about its appeal. The response is written once: the table's key is the invocation and the offer, so a repeat gets 409, even when two copies arrive at the same moment on different workers.
  7. Learn and forget. In one transaction, every belief in that segment shrinks by γ = 0.9998, then this offer's belief takes the reward: α grows by the reward and β by one minus it. Both are computed inside the database from the stored values, so concurrent responses never overwrite each other. A response counts half as much after about 3,500 more updates in its segment, so a belief reflects roughly the last 5,000 responses and can follow a change in taste. The next app open in this segment, on any API worker, reads the new belief at step 3.

A response names only the invocation, the offer and the outcome. The segment and the moment it is learned under come from the context logged at step 4, so a response can't be learned under the wrong segment or the wrong moment.

How we know it works

Real customers can't tell us which offer would have been best. The simulator can. It plays 5,000 synthetic South African customers whose take-up rates come from a hidden table, by segment, offer and moment, with a change in taste halfway through the run. The recommender never sees that table: a test fails if any recommender code imports the simulator or opens its files.

  • Regret is what the oracle measures: after every app open it ranks the offers by their true rates, and the gap between its expected take-ups and those of the three offers actually shown is that app open's regret. Expected values, not one lucky draw, so the curves measure choices rather than luck.
  • A fair race. In each seed every policy faces the identical sequence of customers and moments, so differences come from their choices alone. The static ranking, the batch model a telco might run today, gets a month of history to fit on first; the learning policies start from nothing.
  • Enough runs to trust it. The published comparison runs 10 seeds of 50,000 app opens with the change in taste at the halfway point, and a sensitivity sweep reruns the key policies in six variants of the world. The Results page has the numbers.

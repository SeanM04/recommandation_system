A recommender that learns from every response

A small, production-minded dynamic recommender for a VodaPay-style telco and fintech super-app. Each app open asks an API for offers, a multi-armed bandit ranks them, and every customer response updates the model straight away.

Independent portfolio project by Sean Mukariri, built for the technical team at ecosystem.Ai. It is inspired by their approach to dynamic recommenders; it does not use their product or APIs.

What happens when a customer opens the app

  1. The app calls POST /invocations with the customer id. The API looks up the customer's profile and adds the moment: day, time of day, payday week and channel.
  2. A bandit policy ranks the offers this customer is eligible for, using what it has learned so far, and returns the top few with an invocation_id.
  3. The customer takes one up, looks without taking it, or doesn't notice it. The app reports each outcome to POST /response.
  4. The policy updates its statistics for that offer and context at once, so the next customer benefits from the last one.

Real customers are replaced by a simulator. It knows the true take-up probabilities, which the recommender never sees, so we can measure exactly how much each approach loses while it learns (regret) and how fast it adapts when tastes change.

Run it

python manage.py migrate          # tables and the 5,000 customers (Postgres from .env, else SQLite)
python manage.py createsuperuser  # your admin account for the dashboard
python manage.py simulate         # a 3-seed comparison and 1,000 app opens through the API
python manage.py runserver        # the API (docs at /docs) and the dashboard, together
python manage.py compare          # the published 10-seed comparison (about 9 minutes)
python manage.py test             # the full test suite

With make: make install, make simulate, make dashboard (make help lists every target). Or the whole system with docker compose up --build. Run & operate has every command, setting and option.

Terms used in these pages

Offer (arm)A product the app can recommend. In bandit terms each offer is an arm the policy can pull.
InvocationOne request for ranked offers, made when a customer opens the app.
ResponseWhat happened to one shown offer: taken_up, viewed or ignored.
Take-up rateShare of shown offers that customers take up.
ContextEverything known at the moment of an app open: the customer's profile plus day, time of day, payday week and channel.
Context keyThe slice of context a policy keeps separate statistics for, such as the segment, or segment and payday week.
Options storeThe model's state: one row of statistics (α, β, pulls, total reward) per policy, context key and offer.
Epsilon-greedyShows the best-known offer most of the time and a random one with probability ε.
Thompson samplingKeeps a Beta(α, β) belief per offer, draws one sample from each belief and ranks by the draws. Uncertain offers get explored naturally.
Forgetting (decay)Shrinks old evidence by a factor γ so the model can follow a change in behaviour.
RegretReward lost compared with an oracle that knows the true take-up probabilities.

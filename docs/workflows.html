Workflows

How work flows through the project

Three loops matter here: the commands that turn config into data and results, the simulation loop that stands in for real customers, and the build loop that every phase goes through before the next one starts.

Command pipeline

Every step is a make target that runs one plain command, so the same steps work by hand where make isn't installed. The top row runs left to right on a clean machine; the bottom row can run at any time.

Simulation loop

Phase 4

Each round is one app open. Rounds are spread evenly over the simulated calendar, so paydays and grant weeks come round at the right rhythm. The steps that touch the hidden truth are shaded amber; everything else is what a real app and recommender would do.

Building a phase

In use

Phases are built strictly in order and the code stays runnable at every step. A phase is done when its tests pass, lint is clean, its decisions are logged and it has been reviewed.

Keeping these docs current

Prose and diagrams are edited by hand when a phase changes the design. Every table that comes from data (offers, segments, effects, take-up rates, favourites, the decision log, tool versions, the test list and the build status) sits between generated markers and is rebuilt from the source:

make docs                              # rewrite generated blocks in docs/*.html
python scripts/build_docs.py --check   # exit 1 if any page is stale

tests/test_docs.py runs the check and also verifies that every link between pages points to a page and section that exists, so stale or broken docs fail the build like broken code.

To mark a phase as built, change its status in PHASES in scripts/build_docs.py and run make docs; the sidebar on every page and the overview update together.

Watching the recommender learn

Five Streamlit pages: the live event log, the head-to-head comparison, the beliefs behind each ranking, the behaviour shift, and a page where you play the customer and watch the model update.

Run it

Built
make install     # once
make simulate    # customers, a 3-seed comparison, 1,000 app opens through the API
make dashboard   # http://localhost:8501

That is the brief's definition of done, verified on a fresh clone with no .env: everything falls back to a local SQLite file and no API server is needed. make simulate takes about four minutes there. Run make compare instead for the published 10-seed results; every results page says which run it is showing.

Live view

App opens and their outcomes as they reach the event log, refreshing every 3 seconds, and the serving policy's current top three offers per context. Start a simulation through the API (python scripts/run_simulation.py --mode api) and watch it fill.

Algorithm comparison

The results table, cumulative regret, take-ups and revenue for any set of policies (each keeps one colour on every chart), and convergence: how many app opens each policy needed before each segment's best offer led, from the start and again after the shift.

Explore vs exploit

Each offer's Beta belief for a chosen policy and context at any point in the run, and how the means moved. Wide curves are offers the policy is still testing; a narrow curve far to the right is one it trusts.

Behaviour shift

For young professionals and families, the share of app opens with the new favourite ranked first, take-up per app open, how many app opens each policy needed to adapt, and which offer led over time.

Try it

Pick a segment, a customer, a policy and optionally the moment; open the app; then take up, view or ignore each offer and see the belief for that offer update. It calls the API server if one is running, otherwise the same FastAPI app inside the dashboard, so the code path is identical. Every click is real learning in the database.

Try itThe APILive

Results files are cached by modification time, so a new make compare or make simulate shows up without restarting the dashboard. Three environment variables redirect everything, which is how the tests isolate it: RECOMMENDER_DATABASE_URL, RECOMMENDER_RESULTS and RECOMMENDER_API_URL.

How it is tested

  • Every page renders, using Streamlit's own test harness, against a throwaway SQLite database (customers plus app opens sent through the API) and a throwaway results folder written exactly as make compare writes it. The real database and results are never touched.
  • Content is checked: the live view's counts, every configured policy in the comparison, and the "run make simulate" message when there are no results.
  • Try it is clicked through: open the app, take up the first offer, and assert that the reward and the updated belief are shown.
  • Screenshots on this page come from make screenshots, which drives the installed Chrome or Edge with Playwright.

Dashboard code lives in dashboard/; its theme in .streamlit/config.toml.

API · Phase 3

The real-time recommender API

Two calls do the work: ask for offers when a customer opens the app, then report what happened to each offer. The model learns from every response before the next request arrives.

Run it

Built
make db      # tables in Postgres (Telco_Dynamic_Recomender) or SQLite
make data    # 5,000 customers into data/customers.csv and the customers table
make run     # API on http://localhost:8000, interactive docs at /docs

FastAPI also serves an interactive version of every endpoint at /docs, generated from the same Pydantic schemas the API validates with.

Endpoints

MethodPathWhat it does
GET/healthLiveness and readiness: is the database reachable, and what is being served.
GET/offersThe offer catalogue.
GET/customersA few customer ids, for trying the API out.
POST/invocationsRank offers for one app open, and log the invocation and every offer shown.
POST/responseRecord what happened to one shown offer, and update the model immediately.
GET/policiesEvery configured policy; any of them can serve a request via ?policy=.
GET/policies/{name}/stateWhat a policy has learned: its rows in the options store.
GET/metricsPer-policy take-up and revenue from the event log; latency per endpoint.

Examples

Ask for offers

curl -X POST http://localhost:8000/invocations \
  -H "Content-Type: application/json" \
  -d '{"customer_id": "C00042", "channel": "app", "number_of_offers": 3}'
{
  "invocation_id": "6f1c2a9e-1b0e-4c8e-9d4f-2f7a0c3b5e11",
  "policy": "thompson_segment_decay",
  "customer_id": "C00042",
  "context": {"segment": "student", "time_of_day": "evening", "day_of_week": "thursday",
              "is_payday_week": false, "channel": "app", ...},
  "offers": [
    {"rank": 1, "offer_id": "data_1gb", "name": "1GB Data Bundle (30 days)", "score": 0.214, ...},
    {"rank": 2, "offer_id": "data_5gb", "score": 0.131, ...},
    {"rank": 3, "offer_id": "airtime_r50_bonus", "score": 0.097, ...}
  ]
}

Add ?policy=static (or any name from GET /policies) to serve one request with another policy, for an A/B test. Add a context object to replay a specific moment: {"day": "2026-09-26", "time_of_day": "night"}.

Report what happened

curl -X POST http://localhost:8000/response \
  -H "Content-Type: application/json" \
  -d '{"invocation_id": "6f1c2a9e-...", "offer_id": "data_1gb", "outcome": "taken_up"}'
{"invocation_id": "6f1c2a9e-...", "offer_id": "data_1gb", "outcome": "taken_up",
 "policy": "thompson_segment_decay", "reward": 1.0, "model_updated": true}

Send one response per shown offer: taken_up, viewed (seen, not taken) or ignored (not noticed). An ignored offer is logged but does not update the model by default.

See what the model learned

curl "http://localhost:8000/policies/thompson_segment_decay/state?context_key=student"
curl http://localhost:8000/metrics

Event log

Built

Every invocation, every offer shown and every response is written to Postgres before the model learns, so the log is the source of truth and the options store can be rebuilt from it. The response table's primary key is what makes /response idempotent: the database itself refuses a second row for the same invocation and offer.

Correctness under concurrency

Tested

A real-time API serves many requests at once, and every shortcut that is safe one request at a time can lose or double-count learning when two arrive together. Each risk below has a protection in the database or the code, and a test that fails if the protection breaks. Two of them were found by probing the running system, not by reading the code.

RiskProtectionProven by
Two copies of one response are both countedPrimary key (invocation_id, offer_id) and INSERT … ON CONFLICT DO NOTHING RETURNING: no row back means a duplicate, answered with 409 (decisions A2, A13)8 threads send one response at once: exactly 1 is recorded, on SQLite and Postgres
Two updates to one offer overwrite each otherLearning is one transaction whose statements compute from the row's current value in the database (P11)4 threads × 100 updates: all 400 counted, in memory, SQLite and Postgres
Workers starting together collide creating tablesTable creation holds a Postgres advisory lock (A14)6 processes start at once on an empty schema without an error
Threads share one random generatorEach policy's ranking holds a lock (A9)NumPy generators are documented as not thread-safe
Several workers draw identical Thompson samplesEach server process seeds its own random stream (A15)Seeds differ by process id

Found by probing. On Postgres the driver reports rowcount = -1 for a skipped insert, so the first duplicate check never fired and 8 simultaneous copies of one take-up were learned 8 times. The API tests had only run on SQLite, where rowcount works. Both the check and the test coverage were fixed: the API suite now runs against Postgres too.

Latency

Measured

The brief's target is a p95 under 50 ms locally. make benchmark starts a real uvicorn server against Postgres (in a throwaway schema) and, for each level of concurrency, sends app opens with a response for every offer shown.

Concurrent clients/invocations p95/response p95Requests per secondTarget met
111.4 ms11.5 ms113Yes
431.6 ms28.4 ms189Yes
8120.1 ms105.8 ms158No

One uvicorn worker and Postgres 18 on the same laptop, 150 app opens per client · decision A16

Where the limit is. Server-side timings match the client's, and turning off synchronous commits changed nothing, so the database and disk are not the bottleneck. One Python process is CPU-bound at about 5 ms of work per request. The way to scale is more worker processes. The Docker image runs 4, but on this Windows laptop Docker Desktop made things slower, because every database call crosses from its Linux VM to Postgres on Windows. On Linux, with the database on the same network, more workers is the standard answer; Phase 6 measures it with docker-compose.

What limits throughput

p95 climbs past the target at 8 concurrent clients. Each likely cause was tested on its own:

SuspectTestResult
Forgetting's extra row updatesSame load with a policy without forgetting, and with random, which never touches the storep95 101 and 95 ms against 100 ms: not the cause
Waiting for disk on every commitRerun with synchronous_commit=offNo improvement: not the cause
The load generatorCompare the server's own timings with the client'sServer p95 165–175 ms against client 170–180 ms: the time is spent in the server
Per-request Python overheadPure ASGI timing middleware, one joined query, SQL aggregateThroughput unchanged (113, 189, 158 req/s): not the main cost
One Python process is CPU-boundElimination: about 5 ms of work per request caps one process near 190 req/sThe limit. More worker processes are the remedy
More workers through Docker DesktopThe same load against 4 workers in a containerSlower on Windows (p95 55 ms at 1 client): every database call crosses the VM boundary

Decision A16 · reproduce with make benchmark and make benchmark-docker

Every response also carries an X-Response-Time-ms header, each request is logged as one JSON line, and GET /metrics reports a rolling p50 and p95 per endpoint for the running server.

Run it in Docker

Built
make docker-build   # image telco-recommender:latest (python:3.12-slim, non-root)
make docker-api     # API on http://localhost:8000 with 4 workers, database from .env

The image holds no secrets: make docker-api passes .env with --env-file and points DB_HOST at host.docker.internal, so the container reaches Postgres on the host. The worker count comes from WEB_CONCURRENCY (4 by default), and a health check calls /health every 10 seconds. See Deployment for what this costs on Windows.

The endpoint table and event-log schema are generated from the code by make docs; the latency figures come from make benchmark.

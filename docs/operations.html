Running the recommender

Start it

Built

Three ways, the same system. Without a .env everything uses a local SQLite file, so a clean machine needs no database server.

Django style, any OS

python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
pip install -e .
python manage.py migrate
python manage.py createsuperuser
python manage.py simulate
python manage.py runserver

runserver starts the API, waits until it answers, then starts the dashboard; Ctrl+C stops both. Keep the virtual environment out of folders that OneDrive or Dropbox sync.

make, Linux or macOS

make install
make simulate
make dashboard

The brief's three commands. On Windows: winget install ezwinports.make, then Git Bash. make help lists every target. Verified in a clean python:3.12 container (decision Q7).

Docker Compose, everything

docker compose up --build
docker compose down --volumes

Postgres, the API, the dashboard and a first simulation, with nothing installed but Docker. See Docker Compose.

Docker Compose

Built

One image serves five services. Two are one-off jobs that run and exit. The database is its own container, separate from any Postgres on the machine, and it is not published on a host port.

docker compose up --build              # start; the API at :8000/docs, the dashboard at :8501
docker compose logs -f simulate        # follow the first simulation
docker compose stop                    # pause, keeping the data
docker compose down --volumes          # remove everything, data included
API_PORT=8010 DASHBOARD_PORT=8510 docker compose up --build   # if the ports are taken

The database password defaults to a development value; set COMPOSE_DB_PASSWORD to change it. The first visit to the dashboard creates the admin account (decision AC3: create it from a terminal before exposing a deployment).

The nightly job

Built

Rolls the event log up into one row per day, policy, segment and offer, so reports and drift alerts never scan the raw log. A day is a calendar day in Johannesburg time, and each outcome counts on the day of the app open it answers.

python manage.py nightly             # yesterday
python manage.py nightly --all       # every day in the log
5 0 * * *  cd /path/to/repo && python manage.py nightly    # cron, five past midnight

Rebuilding a day replaces it in one transaction, so a failed run is fixed by running it again, and late responses are picked up by rerunning yesterday. It is a plain script, so cron or a single Airflow task can run it (decision Q6).

Watching it run

  • Logs: one JSON line per request and at start-up, ready for any log shipper: 
    {"ts": "2026-10-15T19:47:58.095+00:00", "level": "info", "logger": "recommender.api",
 "event": "request", "endpoint": "POST /response", "status": 200, "ms": 50.18}
  • GET /health: whether the database answers, the version and the serving policy. Open to everyone, also when API keys are on.
  • GET /metrics: app opens, outcomes, take-up and revenue per policy from the event log, and p50 and p95 latency per endpoint since start.
  • X-Response-Time-ms: on every response.
  • The dashboard's Live view: the latest app opens and what the serving policy believes, every 3 seconds.

Performance, and what load found

Measured

The target is a p95 under 50 ms. Measured with scripts/benchmark_api.py: concurrent clients each open the app and respond to every offer shown.

p95 of POST /invocations and requests per second · decisions A16 and Q3 · details on the API page

Load testing found four things that reading the code had not:

  1. A deadlock. With 4 workers and 16 clients, two forgetting updates to the same segment locked its rows in different orders and Postgres aborted one. Updates to one segment now take a lock of their own first; the rerun had none from 1 to 16 clients (decision Q2).
  2. A misleading 45 ms. From the host, the containers looked slow. In-process the endpoint takes 10 ms and a database round trip 0.34 ms; the extra time was Docker Desktop's port forwarding on every POST. The earlier explanation, database calls crossing the VM, was wrong and is corrected (decisions A16 and Q3).
  3. Commits to a virtual disk. Past four clients, durable commits to Docker Desktop's disk dominate. They stay on: the event log is the source of truth.
  4. One worker restart. Once, at 16 clients, uvicorn restarted a worker that missed its 5-second health ping, dropping its open connections. Not seen again; a production load test should size workers to CPUs (decision Q4).

Two more from running the dashboard on a small machine: it now shares one read-only copy of each results file instead of one per page load (the per-app-open log is 450,000 rows), and SQLite writers wait up to 30 seconds for the write lock instead of 5.

Security

  • People sign in to the dashboard; passwords are salted scrypt hashes, checked in constant time. Viewers see results; admins also use Try it and manage users (decisions AC1–AC4).
  • Programs can be required to send an API key; keys are stored as hashes, shown once and revocable (AC5, API keys).
  • Secrets stay in the git-ignored .env; the Docker image holds none and runs as a non-root user.
  • Tests never touch real data: they use throwaway Postgres schemas and temporary SQLite files.

Production would add single sign-on, a secrets manager, HTTPS and an authenticating proxy; the decision log records each limit of what is built.

# Decisions log

Ambiguities in the brief, the default I picked, and why. Newest at the bottom of each section.

## Setup

| # | Decision | Why |
|---|----------|-----|
| S1 | The repository root is this folder; there is no nested `telco-dynamic-recommender/` directory. | The folder already existed with a `.gitignore`. Nesting would add a level with no benefit. |
| S2 | Exact-pinned dependencies in `requirements.txt` (`==`). | "Works on a clean machine" and reproducible results matter more than picking up new minor versions. |
| S3 | `httpx2` instead of `httpx` for FastAPI's `TestClient`. | Starlette deprecates `httpx` for its test client and emits a warning; `httpx2` is the recommended replacement. |
| S4 | On Windows/OneDrive, create the local virtualenv **outside** OneDrive (for example `%USERPROFILE%\.venvs\telco-recommender`). | OneDrive sync locks files inside `.venv` and `pip install` fails with `WinError 32`. This does not affect Docker. |
| S5 | `make` is the documented interface; every target is a single plain command, so it can be run by hand where `make` is not installed (for example Windows without Git-Bash make). | Keeps one source of truth for commands. |
| S6 | On Windows, keep the virtualenv path short (for example `C:\Users\<you>\.venvs\telco-recommender`). | Streamlit ships deeply nested files; in a long path they exceed Windows' 260-character limit and `pip install` fails with `WinError 206`. |

## Phase 1: Domain and data

| # | Decision | Why |
|---|----------|-----|
| D1 | A customer has a **static profile** (segment, device tier, prepaid/contract, monthly spend, province, *usual* time of day). `time_of_day`, `day_of_week` and `is_payday_week` are **per-session context**, derived when the app is opened (from the simulated calendar, or the server clock in the API). | These change between app opens. Storing them on the customer would freeze "the moment" the recommender is meant to react to. |
| D2 | Payday week: salaried segments from the 25th to month end; pensioners on SASSA grant days 1–7. | Matches South African pay patterns and makes payday a real contextual signal that differs by segment. |
| D3 | The hidden truth lives in `config/ground_truth.yaml` and is used only by `recommender.simulator` and offline evaluation. A test fails if any other `recommender` module imports the simulator. | Enforces "the recommender never reads the true probabilities" with a test rather than relying on convention. |
| D4 | Truth model: `base[segment][offer]` × multiplicative context effects (payday, time of day, weekend, device, contract, spend band, province), capped at 0.9. | One readable table plus a short list of named effects that a reviewer can reason about. |
| D5 | Take-up rates of roughly 2–20%, higher than the 1–5% typical in practice. | 50,000 simulated rounds are then enough to show convergence. The relative patterns matter, not the absolute levels. |
| D6 | Segment eligibility (`offers.yaml`) is a business rule the recommender **may** use. The ground truth defines probabilities for eligible pairs only, and this is validated on load. | Eligibility is public business logic; the probabilities are not. |
| D7 | Behaviour shift: young professionals' `streaming_bundle` base rate goes from 5% to 20% and their `data_5gb` drops from 13% to 8% (cannibalisation); students' streaming rises from 8% to 12%. | Flipping the favourite in the largest segment is the clearest adaptation test. Because the old favourite also gets *worse*, models that never forget are penalised. |
| D8 | The customer table is a CSV (`data/customers.csv`), regenerated deterministically from the seed and git-ignored. | Small, inspectable and reproducible. It can be loaded into SQLite or Postgres later. |
| D9 | Prices for cover products are monthly premiums; the savings pocket "price" is its minimum deposit. All prices and margins are illustrative. | Keeps `margin_zar <= price_zar` meaningful for every offer. |
| D10 | Generic names for third-party products ("Music + Video Streaming Bundle", "Food Delivery Voucher"). | Avoids implying real partnerships. |
| D11 | Population, the ground-truth path and the calendar live in `config/simulation.yaml`, loaded only by `recommender.simulator`. The recommender's `settings.yaml` has no path to the truth, and a test fails if recommender code mentions `ground_truth` or `simulation.yaml`. | Hiding the truth is enforced for file reads as well as imports. |
| D12 | The simulated calendar is 60 days from 2026-09-01: two salary paydays and two SASSA grant weeks. | Payday effects get exercised twice, and the shift can sit at the halfway point. |
| D13 | Payday **changes the favourite** in two segments. Pensioners: airtime for the rest of the month, electricity in grant week. Small businesses: pay-later in the mid-month cash squeeze, 20GB data in payday week. Other segments keep one favourite. | Without this the segment × payday context mode has nothing to learn and would lose to plain per-segment mode, because it splits the data for no benefit. |
| D14 | Funeral cover margin raised from R40 to R50. Every favourite, by take-up or by revenue, leads its runner-up by at least ×1.2 (tested). | Removes the family revenue near-tie (×1.02), which would have stopped any policy from settling. Revenue changes the favourite for students (5GB), young professionals (20GB), small businesses (20GB) and pensioners (funeral cover), which makes the revenue-aware reward worth demonstrating. |
| D15 | **Response model for a ranked list** (in the ground truth): the customer scans from the top and notices position k with probability `attention = [1.0, 0.6, 0.4, 0.25, 0.15]`. A noticed offer is taken up with its true probability, and the first take-up ends the visit. Outcomes: noticed and taken = `taken_up`; noticed, not taken = `viewed`; not noticed (or below a take-up) = `ignored`. | Gives the API's three outcomes a precise meaning and makes position matter, so ranking order affects reward. It is simple enough to compute expected reward exactly, which the regret oracle needs. *Implication for Phase 2:* `ignored` says little about whether an offer appeals, so how policies learn from it has to be a deliberate choice. |

## Phase 2: Algorithms

| # | Decision | Why |
|---|----------|-----|
| P1 | Policies hold no state. The **options store is the model**: one row per (policy, context key, offer). There is one interface with two implementations, in-memory for simulations and SQLAlchemy Core (SQLite now, Postgres by URL) for the API, and both pass the same tests. | A restart, a second API worker or a dashboard all see the same model. Simulations stay fast because they skip I/O. |
| P2 | The store keeps `pulls` and `total_reward`. `alpha = 1 + total_reward` and `beta = 1 + pulls - total_reward` (a Beta(1, 1) prior) are derived, and are still written to the table for anyone querying it. `pulls` is a float. | The Beta belief can never disagree with the counts. With forgetting on, `pulls` becomes an effective count. |
| P3 | Contextual personalisation is a `context` option on each learning policy (`global`, `segment`, `segment_payday`) rather than a separate class. The option becomes the store's `context_key`. | One implementation of each algorithm. Every variant is a line of config, so variants can be compared like for like. |
| P4 | Forgetting: before each update, **every** offer's evidence in that context shrinks by γ towards the prior, and then the new reward is added (discounted Thompson sampling). The same rule applies to epsilon-greedy averages. | Offers that are not being shown must also lose stale confidence, otherwise a once-good offer would keep a high, certain estimate forever. |
| P5 | A reward function maps an outcome to a value in [0, 1], or `None` for no update. `taken_up` scores 1 (binary) or margin ÷ the catalogue's top margin (revenue-aware); `viewed` scores 0; `ignored` makes no update by default (`learn_from_ignored` turns it into 0). | Rewards stay on the scale a Beta belief needs. Skipping `ignored` avoids punishing offers for a low rank (decision D15). |
| P6 | Epsilon-greedy fills the slate one slot at a time: each slot explores with probability ε, otherwise takes the best average. Untried offers score 1.0 so each is tried early, ties break randomly, and ε can decay with the evidence in the context (`ε × decay^pulls`, floored at `min_epsilon`). | The textbook algorithm extended to a ranked list, with every behaviour visible in about 20 lines. |
| P7 | The static baseline is one global popularity table (average reward per offer), fitted from a historical log by `StaticPolicy.fit` and then frozen. With no history it uses catalogue order. Phase 4 fits it on a warm-up batch. | A fair stand-in for a batch-trained model: it learned from real data once, then stopped. |
| P8 | Each policy gets its own random stream, seeded from the global seed and a hash of its name. | Results are reproducible, and adding or removing one policy never changes another's results. |
| P9 | **Default forgetting is γ = 0.9998.** A first single-seed run showed that Thompson sampling *without* forgetting adapts to the streaming hit on its own, because a rarely shown offer keeps a wide belief and keeps being tested. So the shift gained a second event: families' well-known runner-up, electricity cashback, overtakes funeral cover (base 10% to 20%). `make experiment` (`scripts/experiment_forgetting.py`) now reruns the comparison: 50,000 app opens, 3 offers each, shift at 25,000, 5 seeds, mean (sd). No forgetting: families' new favourite ranked first in 0.15 (0.20) of their app opens after the shift, young professionals' in 0.81 (0.17); take-up per open 0.235 before, 0.287 after. γ = 0.9998: 0.74 (0.11) and 0.94 (0.02); take-up 0.231 before, 0.294 after. γ = 0.9995 adapts about as well but costs more before the shift (0.226); γ = 0.999 is worse on both. | Forgetting pays off when the model is *confident* about something that changes, and the evidence now comes from a script anyone can rerun, across seeds, rather than one lucky run. Without forgetting the outcome is also far less predictable (sd 0.20 against 0.11). |
| P10 | Default slate size is 3 offers per app open (`number_of_offers`). | Matches a phone screen's offer carousel and the attention model's first three positions. |
| P11 | **Learning is one atomic store operation**, `learn(policy, context_key, offer_id, reward, decay)`. In SQL it is one transaction: an `UPDATE ... SET pulls = pulls * γ` over the context, then an `INSERT ... ON CONFLICT DO UPDATE SET pulls = pulls + 1`. Both compute from the row's current value inside the database. The in-memory store uses a lock. | The first version read the row, changed it in Python and wrote it back. In a test with 4 threads × 150 updates, 445 of 600 updates (74%) were lost. FastAPI runs request handlers on parallel threads, so the API would have silently dropped learning under load. The atomic version passes the same test on memory, SQLite and Postgres, and stays correct with several API workers. |
| P12 | `alpha` and `beta` are **generated columns** (`GENERATED ALWAYS AS (1 + total_reward) STORED` and `1 + pulls - total_reward`), computed by the database. | The database itself guarantees the Beta belief matches the counts, for anyone querying the table directly. |
| P13 | The simulation loop lives in `recommender/simulator/engine.py` (fast mode: the policy is called directly) and is shared by the forgetting experiment and the tests. Phase 4 adds the same loop through the API. | One loop, not a copy per script, so experiments and tests measure the same thing. |
| P14 | One list of context modes (`CONTEXT_MODES` in `domain.py`), used by the policies and by settings validation. The policy attribute is `context_mode`, so it is never confused with a `Context` object. | Removes a duplicate list that could drift, and a name a reviewer would trip over. |

## Phase 3: Real-time API

| # | Decision | Why |
|---|----------|-----|
| A1 | The event log is three normalised tables: `invocations` (one row per app open, with the full context as JSON), `impressions` (one row per offer shown: position and score) and `responses` (one row per outcome). | Plain SQL can answer "take-up by position, offer, policy or segment" without unpacking blobs, and the nightly aggregation job (Phase 6) has clean inputs. The stored context is exactly what the policy learns from when the response arrives. |
| A2 | **Idempotency is enforced by the database.** `responses` has the primary key `(invocation_id, offer_id)`, and the insert is `ON CONFLICT DO NOTHING`; zero rows written means a duplicate, answered with 409. | Correct even when two copies of the same response arrive at the same moment, or land on different API workers. A read-then-check in Python would not be. |
| A3 | **Log first, then learn.** A response is written to the event log before the model is updated. | If the update fails, the record survives, and the options store can be rebuilt by replaying `responses`. The log is the source of truth; the model is derived from it. |
| A4 | The policy that served an invocation is stored with it and is the one that learns from its responses. | A/B arms chosen with `?policy=` learn only from their own traffic, so comparisons stay clean. |
| A5 | Customers live in a `customers` table. `make data` loads it, the API does one primary-key lookup per request, and an empty table is filled from `data/customers.csv` on first start. | Real profile lookups instead of an in-memory file. This resolves the Phase 1 item to move customers into the database. |
| A6 | The moment of an app open is "now" in `Africa/Johannesburg` (the `timezone` setting). A request may override `day`, `time_of_day` and `is_payday_week`, and the override is logged with the invocation. | South African paydays and times of day are local. The simulator (Phase 4) and the dashboard need to replay specific days. |
| A7 | Error handling: 404 for an unknown customer, invocation, offer, policy or segment; 409 for a duplicate response; 422 for a malformed body, an unknown field (`extra="forbid"`), too many offers, or an offer that was not shown in that invocation. Every error has a readable `detail`. | Clients get a precise reason, and silent mistakes such as a typo'd field name fail loudly instead of being ignored. |
| A8 | The static baseline is fitted at startup from every reward in the log, then frozen until the next restart. | A restart plays the role of the nightly batch retrain, which is exactly the behaviour being compared against. |
| A9 | Endpoints are synchronous, so FastAPI runs them on a thread pool. Learning is atomic in the store (P11), and each policy's ranking holds a per-policy lock because NumPy random generators are not thread-safe. | Correct under concurrent requests without async database drivers. |
| A10 | Timing middleware adds an `X-Response-Time-ms` header, writes a JSON log line per request, and keeps a rolling p50/p95 per endpoint for `/metrics`. **Measured** by `make benchmark` (a real uvicorn server, Postgres 18, real HTTP, a throwaway `benchmark` schema), with 1,000 app opens and 3,000 responses from a sequential client after 20 warm-up opens. Client-side p95 was 12.4 ms for `/invocations` and 13.5 ms for `/response`; server-side p95 was 10.1 ms and 11.2 ms. | The brief's target is p95 under 50 ms locally; it is met with roughly 4× headroom. The number comes from a rerunnable script, not an estimate. |
| A11 | Logs are JSON lines (`recommender/observability.py`), and uvicorn's own access log is turned off (`--no-access-log`) because the middleware logs every request. | One structured line per request that a log pipeline can parse; Phase 6 builds on this. |
| A13 | **Duplicate detection uses `RETURNING`, not `rowcount`.** A concurrency probe showed that on Postgres the driver reports `rowcount = -1` for `INSERT ... ON CONFLICT DO NOTHING`. The duplicate check never fired, so 8 simultaneous copies of one take-up were all accepted and learned 8 times. Now the insert returns the key, and no row back means a duplicate. The API and event-log tests run on Postgres as well as SQLite, including 8 threads sending one response at once: exactly one is recorded. | Idempotency is a hard requirement, and the bug only existed on the production database, which the tests had not covered. |
| A14 | **Table creation runs under a Postgres advisory lock** (`pg_advisory_xact_lock`). | With 4 worker processes starting on an empty database, each tried to create the tables, Postgres rejected the duplicates, and uvicorn stopped the whole server. Now one process creates the tables and the others wait and find them there. A test starts 6 at once. |
| A15 | **Docker image**: `python:3.12-slim`, a non-root user, a `/health` health check, 4 uvicorn workers by default (`WEB_CONCURRENCY`). Secrets come from `--env-file .env` with `DB_HOST=host.docker.internal`, never baked in. Each server process seeds its own random stream. `make docker-build`, `make docker-api`, `make benchmark-docker`. | The API can be deployed separately as a container, and several workers never draw identical Thompson samples. |
| A16 | **Capacity, measured.** Native, one worker, Postgres on the same laptop (`make benchmark`): p95 11.4 ms at 1 client (113 req/s), 31.6 ms at 4 clients (189 req/s), 120 ms at 8 clients (158 req/s). Server-side timings match the client's, and `synchronous_commit=off` changed nothing, so one Python process is CPU-bound at about 5 ms of work per request. Docker Desktop with 4 workers was *slower* on this laptop (p95 55 ms at 1 client, 81 req/s at 8), which I put down to every database call crossing from the Linux VM to Postgres on Windows (wrong: Phase 6 found the cause in Docker Desktop's port forwarding, see Q3); one run also stalled when Docker Desktop froze for over an hour. | The 50 ms target holds for up to 4 concurrent clients, which covers the simulator and a local demo. Beyond that the answer is more processes on Linux, with the database on the same network (to measure with docker-compose in Phase 6). Production would add PgBouncer connection pooling and batched event writes. |
| A12 | Added `GET /customers` (a few ids, optionally per segment), which the brief does not list. | Needed to try the API by hand and for the dashboard's "pick a customer" page. |

## Phase 4: Simulator and comparison

| # | Decision | Why |
|---|----------|-----|
| C1 | **Regret against an oracle, from expected values.** For each app open the oracle ranks eligible offers by true probability, and regret is the oracle's expected take-ups minus the expected take-ups of the list the policy showed, both from the response model. The revenue oracle ranks by probability × margin. | Expected values measure the policy's choices rather than the luck of one draw, so curves are smooth and seeds agree. Ranking by p × margin is not exactly optimal under the attention model, but it is close and identical for every policy. |
| C2 | **Common random numbers.** Arrivals (customer, day, time of day) and customer responses use separate random streams, so every policy run with a seed faces the identical sequence of app opens. | Differences between policies come from their decisions, not from different customers. A test checks the sequences match. |
| C3 | **A fair batch baseline.** The static policy is fitted on a warm-up month (5,000 app opens served by a random policy, before the shift), then frozen. The learning policies start with no data. | The static model gets the history a real batch model would have; the bandits still beat it. |
| C4 | Every comparison runs **10 seeds**. The table reports the mean and spread, and every finding is a **paired** comparison: within a seed both policies faced the same app opens, so the findings say in how many seeds a difference holds and call a tie a tie. | With 3 seeds, a first draft claimed `thompson_segment_decay` "wins" and that forgetting "halved the spread". Seed by seed, the first held in only 1 of 3 seeds and the second rested on three numbers. Paired counts over 10 seeds show what is real. |
| C5 | **Fast mode is the default** (about 9,000 app opens a second, 50,000 in roughly 5 s). **API mode** (`--mode api`, default 5,000 app opens) sends real HTTP calls with the simulated day and time as context overrides, so the database fills with live-like traffic. `--persist` copies a fast-mode model into the database. | Large comparisons need speed; the API path proves the same loop works end to end, and its events feed the dashboard's live view. |
| C6 | Results go to `results/` (git-ignored: CSV, Markdown, per-app-open Parquet and belief snapshots) and a summary to `docs/data/comparison.json` (committed). The Results page, its chart and the findings are generated from that file. | Published numbers always match the last `make compare`, and the docs check keeps them consistent. |
| C7 | **Results** (50,000 app opens, shift at 25,000, 10 seeds). Per-segment Thompson sampling reached about 92.5% of the oracle and cut regret by 84–85% against random and 80–81% against static, in 10 of 10 seeds; static reached 60.8% and global Thompson 67.7%. The three per-segment Thompson variants are tied overall. Forgetting lowered regret after the shift in 10 of 10 seeds (by 130 take-ups on average) at a cost of 93 before it. Thompson beat epsilon-greedy with the same segments in 8 of 10 seeds. | The definition of done is met: contextual Thompson sampling beats both baselines in every run and adapts after the shift, while the static model does not. |
| C8 | **The reward is set per policy** (`reward: margin` in `settings.yaml`, defaulting to `recommendation.reward`), and the comparison, simulator and API all use it. `thompson_segment_revenue` is the same policy as `thompson_segment_decay` but learns from margin: 38% more revenue per app open (R13.37 against R9.68, more in 10 of 10 seeds) for 22% fewer take-ups. | The brief asks for a pluggable reward; the comparison now shows what it changes. Choosing between take-ups and revenue is a business decision the system makes explicit. |

## Phase 5: Evaluation and dashboard

| # | Decision | Why |
|---|----------|-----|
| E1 | **Convergence** = app opens until each segment's best offer *for the moment* (segment and payday week) led in 80% of that segment's last 100 app opens, counted from the start and again from the shift; "not within the run" otherwise. | Judging against the moment's answer gives payday-aware policies credit for switching, and the after-shift count is the brief's "adaptation speed". The 80% / 100 thresholds are a judgement call, stated wherever the number appears. |
| E2 | **Selection share** = the share of a segment's app opens in which each offer was ranked first, per block of 1,000 app opens. | First position gets every customer's attention, so it is the offer the policy is betting on. |
| E3 | `make simulate` = customers, a 3-seed comparison (`--no-docs`, so the published 10-seed results stay as they are), and 1,000 app opens through the real API app in-process (`run_simulation.py --mode api --in-process`). Verified on a fresh clone with no `.env` (SQLite): about four minutes, then every dashboard page renders. | `make install && make simulate && make dashboard` works on a clean machine with no API server and no Postgres. The live view still gets real events through the API's code. |
| E4 | Results pages read `results/` files cached by modification time, and say which run they show ("N seeds × M app opens, saved at …"). | A new run appears without a restart, and nobody confuses a quick 3-seed run with the published 10-seed results. |
| E5 | **Try it** calls the API server if one answers at `RECOMMENDER_API_URL`, otherwise runs the same FastAPI app inside the dashboard. | Identical code path either way, and the page works with nothing else running. Every click is real learning in the database. |
| E6 | The live view uses plain tables (`st.table`), not interactive grids. | Grids re-mount on every 3-second refresh and flash empty; 15 rows read better as a table. |
| E7 | Dashboard tests use Streamlit's AppTest against a throwaway SQLite database and results folder, redirected with `RECOMMENDER_DATABASE_URL`, `RECOMMENDER_RESULTS` and `RECOMMENDER_API_URL`. They check content and click through Try it. | The first version only checked for exceptions and read the real Postgres. Now nothing real is touched (event counts were identical before and after a test run), and the main user flow is proven. |
| E8 | One fixed colour per policy on every chart (the docs' categorical palette, in order; a ninth policy is grey), and the shift marked on every time chart. | Colour follows the policy, never its rank or the chart, so a reader can follow a policy across pages. |
| E9 | Screenshots come from `make screenshots` (Playwright driving the installed Chrome or Edge). It signs in with an admin account and moves between pages through the sidebar, because a sign-in lasts for one browser session. | Reproducible images for the README and docs without a browser download. |
| E10 | **The comparison page tells a story** (Brent Dykes' data storytelling arc). The headline is the finding. The setting and hook show what was possible against what a fixed ranking gets. Three findings follow, one chart and one message each, with colour only on what the message is about. Then the answer in one sentence, and next steps. Plain names replace policy ids. The full tables are folded away at the end. | A reader who sees the page once should leave with the message, not a table to decode. All the numbers come from `recommender.evaluation.story`, which computes them from the run on disk, counts how many runs back each claim, and says when the top policies tie, so the story can't overstate the evidence. |
| E11 | **Explore vs exploit and Behaviour shift tell stories too,** with the same arc and rules: a headline that is the finding, one chart and one message per finding, colour only on the message, offers and policies by name, and the detail in an expander. Exploration is measured as the share of each segment's app opens whose first offer wasn't the one the policy showed first most often in that period of 2,500 app opens. The chance of being best comes from the learner's own Beta beliefs. | Thompson sampling shows an offer first as often as it might be the best, so the chance of being best is how much it explores, offer by offer. The exploration share needs no ground truth. In the period right after the shift it also counts switching, because the old and new favourites share that period, and the page says so rather than calling it all exploration. The numbers come from `recommender.evaluation.exploration` and `recommender.evaluation.adaptation`. |

## Phase 6: Quality and delivery

| # | Decision | Why |
|---|----------|-----|
| Q1 | **The whole system with one command:** `docker compose up --build` (or `make up`). One image serves five services: Postgres 17, a one-off `init` job (the customers), the API with 4 workers, the dashboard, and a one-off `simulate` job. That job sends 1,000 app opens through the API over the network, then runs a 3-seed comparison. | A reviewer needs nothing but Docker. The compose database is separate from the local `Telco_Dynamic_Recomender` (no secrets, nothing to collide with) and isn't published on a host port; `docker compose down --volumes` removes everything. Host ports can be moved (`API_PORT`, `DASHBOARD_PORT`) because 8000 is often taken. |
| Q2 | **A deadlock under real concurrency, fixed with a lock per context.** The first compose benchmark (4 workers, 16 clients) failed with `deadlock detected`. Postgres's log showed two forgetting updates to the same segment locking its rows in different orders ("while rechecking updated tuple"). With forgetting on, `learn()` now first takes `pg_advisory_xact_lock(hashtext(policy), hashtext(context_key))`. The rerun had no deadlocks from 1 to 16 clients. | Forgetting writes every row in the context, so updates to one context already waited on each other; the lock only fixes the order, at no cost. A retry loop would have hidden the cause and wasted work. A new test runs 16 threads × 60 updates across 12 offers in one context on every store, and checks that nothing fails or is lost. It doesn't reproduce the deadlock on this laptop (the timing needs Docker's slow disk), so the compose rerun is the evidence for the fix. |
| Q3 | **Latency, measured where it is honest.** From the host, the compose API looked slow (p50 55 ms). But in-process the endpoint takes 10 ms and a database round trip 0.34 ms. Measured from a container on the same network, with durable commits, p95 was 15 ms at 1 client (80 req/s), 22–25 ms at 4 clients (224 req/s), about 100 ms at 8 (116 req/s) and 134–139 ms at 16 (167 req/s). With `synchronous_commit=off` it was 12, 19 and 38 ms at 1, 4 and 8 clients (291 req/s). `scripts/benchmark_api.py --url` measures any running API; `make benchmark-compose` runs it from the host. | Docker Desktop's port forwarding on Windows adds about 45 ms to every POST but not to GETs, consistent with a Nagle/delayed-ACK stall in its proxy. That is not part of the system, and a Linux server doesn't have it. Past 4 clients, commit flushes to the VM's virtual disk dominate. Durable commits stay on, because the event log is the source of truth: `synchronous_commit=off` (losing the last few hundred milliseconds of commits on a crash) is a production lever to choose deliberately. |
| Q4 | Once, at 16 clients through the port forwarding, uvicorn's supervisor restarted a worker that missed its 5-second health ping, which dropped that worker's open connections. It didn't happen in three later runs. | Left at uvicorn's default. A production load test should size workers against CPUs and revisit `--timeout-worker-healthcheck`. |
| Q5 | The results table and findings in README.md and WRITEUP.md are generated from `docs/data/comparison.json` by `make docs`, between the same marker comments as the HTML docs. `tests/test_docs.py` fails if they are stale. | The numbers in the first thing a reviewer reads can't drift from the published run. |
| Q6 | **The nightly job is a script, not an Airflow DAG.** `scripts/nightly_aggregate.py` (`make nightly`) rebuilds one day of `daily_offer_stats` in a single transaction: delete the day, insert its aggregate, with the counts done by the database in one query. A day is a calendar day in `Africa/Johannesburg`, and outcomes count on the day of the app open they answer. | Cron or a single Airflow task can run it unchanged. Adding Airflow would have brought a heavy dependency and code I couldn't test here. Rebuilding a whole day makes reruns safe and picks up late responses. Counting outcomes on the app-open day keeps each day's funnel (shown, then taken up) consistent. |
| Q7 | Windows doesn't ship `make`, and this laptop doesn't have it. The README points to `winget install ezwinports.make`. The definition of done is verified in a clean Linux container: a fresh clone in `python:3.12`, then `make install && make simulate`, then the dashboard. | The brief's three commands are the contract, and a fresh container is the most faithful clean machine. |

## Accounts and access

| # | Decision | Why |
|---|----------|-----|
| AC1 | **Accounts live in the project database** (`users`, `api_keys`). Passwords are salted scrypt hashes from Python's standard library, checked in constant time; signing in as an unknown user costs the same work as a real check. | No new dependency and nothing outside the project to set up. Streamlit's built-in sign-in needs an identity provider (Google, Microsoft) registered first: the right choice for production single sign-on, too much setup for this deadline. |
| AC2 | **Two roles.** Viewers see the live view and the results. Admins also get Try it, which changes the model, and Users and API keys. Admin pages are left out of a viewer's navigation, and each also checks the role itself. | Read-only access is the common case; changing the model or the accounts is not. The second check means a page can't be reached by accident. |
| AC3 | **The first admin:** `python manage.py createsuperuser`, or the dashboard's first screen, which appears only while no account exists. | The brief's three commands still work on a clean machine. On a fresh deployment open to others, though, the first visitor could claim admin, so create the admin from the terminal before exposing it. |
| AC4 | **A sign-in lasts for the browser tab** (Streamlit's session state), and reloading asks again. Five failed sign-ins lock the tab for 30 seconds. | Simple and has no cookies to secure. Persistent sessions, and lockouts that survive a reload, come with single sign-on or an authenticating proxy in production. |
| AC5 | **API keys are optional** (`RECOMMENDER_REQUIRE_API_KEY`, off by default). Each key is 32 random bytes, shown once and stored as a SHA-256 hash, and can be revoked. Every endpoint but `/health` checks the `X-API-Key` header. The dashboard, simulator and benchmark send `RECOMMENDER_API_KEY`. | Off by default so nothing breaks on a clean machine; one setting turns it on. A fast hash is enough for long random keys, unlike passwords. `/health` stays open for load balancers. |
| AC6 | **`python manage.py`**, Django style: `migrate`, `createsuperuser`, `createuser`, `changepassword`, `users`, `createapikey`, `runserver`, `simulate`, `compare`, `nightly`, `test`. `runserver` starts the API, waits until it's healthy, then starts the dashboard. It refuses ports already in use, naming the setting to change, and Ctrl+C stops both. | Works on Windows without `make`, and the dashboard decides once at startup whether to call the API over HTTP. Writing its tests also turned up a real bug: on a fresh database the dashboard could start before the API had created the tables, so the dashboard now creates any missing tables itself. |

## Database

| # | Decision | Why |
|---|----------|-----|
| DB1 | The project database is **Postgres `Telco_Dynamic_Recomender`** on this machine (created in pgAdmin, Postgres 18). Connection settings live in a git-ignored `.env`, either as `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `DB_PORT` (the URL is built from them, so special characters in the password need no escaping) or as one `RECOMMENDER_DATABASE_URL`, which takes precedence. `.env.example` is the template. With neither, the same code uses a local SQLite file. | Credentials never enter the repository. The `DB_*` form is the convention most teams already use. A reviewer's clean machine still runs with no database server. |
| DB2 | Driver: psycopg 3 (`psycopg[binary]`), through SQLAlchemy Core. The only dialect-specific code is the `ON CONFLICT` upsert, which Postgres and SQLite both support. | One code path for both databases; no ORM in the hot path. |
| DB3 | `make db` (`scripts/init_db.py`) creates any missing tables and copies a local SQLite model into Postgres if one exists. It is safe to rerun. Alembic migrations are deferred while the schema only grows. | A one-command, repeatable setup and migration. Versioned migrations become worth it once a column changes, not before. |
| DB4 | Tests run against Postgres too, in a throwaway schema `pytest_recommender` that is created and dropped around each test. They are skipped when no Postgres URL is configured. | The real tables are never touched by tests, and a machine without Postgres still runs the full suite. |

## Documentation

| # | Decision | Why |
|---|----------|-----|
| DOC1 | The docs are a static HTML site in `docs/`: six pages, one stylesheet, no build step and no JavaScript libraries. Diagrams are hand-drawn inline SVG. | Opens offline straight from the file system, deploys to GitHub Pages unchanged, and follows the reader's light or dark theme. SVG diagrams stay crisp and change in the same diff as the code they describe. |
| DOC2 | Every data table in the docs (offers, segments, effects, take-up rates, favourites, this log, tool versions, tests, build status) is generated from the code by `scripts/build_docs.py` between marker comments. `tests/test_docs.py` fails if a page is stale, a link or anchor is broken, or an id repeats. | Docs as code: the numbers a reviewer reads are the numbers the simulator uses, and stale docs fail the build like broken code. |
| DOC4 | `docs/data/` is tracked; ignore rules for generated data are anchored to the project root (`/data/`, `/results/`). | The unanchored `data/` rule also matched `docs/data/`, so the Results page's data had never been committed and a fresh clone could not rebuild it. |
| DOC3 | The README carries its own Mermaid architecture diagram. | GitHub renders Mermaid inside Markdown, and the README is the first thing a reviewer sees. |
| DOC5 | **A Claude Code hook requires a docstring on every function Claude writes** (`.claude/hooks/require_docstrings.py`, registered in `.claude/settings.json`). After each Write or Edit of a Python file, it checks the functions whose `def` is in the new text and reports any without a docstring back to Claude, which adds them before carrying on. Functions named `test_*` are exempt. | Enforced at the moment the code is written, not in review. Checking only new functions keeps a one-line fix from turning into a sweep of the whole file. Test names already say what they check. The hook uses only the standard library, and `tests/test_docstring_hook.py` covers it. |

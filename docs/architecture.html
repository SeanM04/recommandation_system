Architecture

How the pieces fit together

Two worlds share one repository: the recommender, which has to learn, and the simulated world, which knows the answers. Everything here is designed so the first can never peek at the second.

System overview

The simulator plays the part of the app and its customers. It calls the recommender over HTTP exactly as a real app would, so the API, policies and stores are exercised the same way in a simulation run as they would be in production.

Life of one request

Built

Ranking and learning happen inside the request path. There is no nightly retrain: the statistics a policy uses for the next customer already include the last customer's response. The target was a p95 latency under 50 ms locally; measured end to end on Postgres it is about 13 ms (details).

Keeping the truth hidden

Built

A recommender that could read the true probabilities would look perfect and prove nothing. Three layers stop that from happening by accident:

  • Separate files. The recommender's settings.yaml has no path to the truth. The simulated world is configured in simulation.yaml and ground_truth.yaml, which only recommender.simulator loads.
  • An import guard. A test parses every recommender module and fails if any imports recommender.simulator.
  • A text guard. A second test fails if any recommender module so much as mentions ground_truth or simulation.yaml, which catches a file read that an import check would miss.

Deployment

Built

The API runs two ways: as one local process (make run), or as a container with four worker processes (make docker-api). Both use the same Postgres database. The difference that matters on this laptop is the path every database call takes.

Storage design

Built

Postgres, in the Telco_Dynamic_Recomender database, through SQLAlchemy Core. When no database URL is configured the same code runs on a local SQLite file, so a clean machine needs no server. The options store is the model; the event log is the audit trail it can be rebuilt from.

  • Learning is atomic. One transaction shrinks the context's evidence and adds the new reward, each computed from the row's current value inside the database, so simultaneous requests can't overwrite each other. A first version lost 74% of updates under four concurrent threads; see decision P11.
  • The database keeps the belief consistent. alpha and beta are generated columns computed from pulls and total_reward.
  • Setup is one command. make db creates missing tables and copies a local SQLite model into Postgres if one exists.
Options store, one row per policy × context key × offer. The primary key is the first three columns.
